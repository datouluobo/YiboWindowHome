# 100%／150% 实机恢复验证

日期：2026-10-27。用户手动调整缩放，测试程序只操作自建非激活窗口与独立记录。实际拓扑为 DISPLAY1 144 DPI、DISPLAY2 96 DPI，分辨率均 2560×1440，工作区分别为 2560×1368、2560×1392。

## 结果

13 组独立原生窗口场景全部通过，恢复前后的原记录 SHA256 均不变：

| 场景 | 数量 | 核对结果 |
| --- | --- | --- |
| 原 125%／125% 记录，在新混合环境恢复 | 5 | 两个方向的普通、最大化，以及跨屏布局降级；状态为 Adapted，实际边界符合换算计划 |
| 当前混合环境记录后跨屏恢复 | 5 | 两个方向的普通、最大化，以及跨屏原矩形；状态为 Restored，物理边界精确一致 |
| 等覆盖面积、从另一屏创建的跨屏窗口 | 1 | 区分锚定显示器 DPI 与窗口通知 DPI，原矩形精确恢复 |
| 分别偏向两屏、覆盖面积不相等的跨屏窗口 | 2 | 原矩形精确恢复，窗口有效 DPI 与实际系统通知一致 |

普通与最大化场景均确认 96→144、144→96 的实际窗口 DPI 变更，收到对应 WM_DPICHANGED。跨屏大窗口在本机可能保持原窗口 DPI；该值属于实际相交屏幕之一，并与通知状态一致。它不强制等于几何锚定屏幕 DPI，物理矩形要求保持不变。

另使用明确声明 PMv2、目标 .NET Framework 4.8 的 WPF 与 WinForms 夹具，完成两个方向的普通/最大化恢复共 8 个组合，均通过。核对窗口 DPI 确实从来源屏幕变为目的屏幕，并检查最大化后再还原的普通边界。

- `build/manual-display/real-mixed-20261027-164706/verified-100-150-results.json` 汇总 13 组原生案例；各目录保留捕获文件及逐步 JSON。
- `artifacts/mixed-dpi-full-regression.txt` 为当前整组回归，14 套件、254 个 PASS 断言，0 失败、0 跳过，49.96 秒；框架双向检查在 native_core 中。

## 修正

1. 测试工具原先将锚定显示器 DPI 与跨屏窗口有效 DPI 直接相等作为通过条件，这超出了物理矩形恢复约定。现分别记录锚定 DPI、Windows 监视器判定、窗口实际 DPI 和原生通知；窗口使用独立消息线程，处理真实 DPI 通知。单屏和最大化的目标 DPI 仍严格检查。
2. 实测发现 WM_NULL 响应可能先于异步位移完成，导致随后最大化读取旧矩形并错误建立普通边界。窗口操作现在在有界时间内观察实际几何和 DPI 稳定后继续，保留每次响应探测的超时约束；应用拒绝尺寸时交由恢复服务返回 Limited。
3. 最大化前的普通尺寸受应用限制时，恢复服务不能报告精确成功，已增加 Limited 检查。原生集成亦改为由窗口自身建立预先置顶状态，再验证恢复是否保留它，防止测试设置阶段未生效被误计为恢复失败。
4. 托管夹具加入正式 PMv2 清单、.NET Framework 4.8 声明和 WinForms 高 DPI 配置；不把仅处于系统 DPI 模式的跨屏移动冒充应用级 DPI 切换。

依据：[WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged)、[WinForms 高 DPI 支持](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/high-dpi-support-in-windows-forms)。
