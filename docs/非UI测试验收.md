## 本轮发现并修复

初始 WM_NULL 响应探测不能保证下一条布局调用不阻塞：测试目标在 WM_WINDOWPOSCHANGING 卡住时，旧恢复代码一直等到 500 ms 的测试保护线程放行。旧结果：`artifacts/native-position-hang-before.txt`。

现在对外部线程的位移、置顶、显示状态和预览还原使用异步请求及有界响应检查；不附加输入队列。WPF 重复回归证实初始化完成后的正常恢复可耗时约 95–97 ms，原 80 ms 等待会偶发错误判定失败。外部操作的单次响应探测超时参数统一为 200 ms，保留异步请求与有限检查；不改变按钮跟随刷新间隔。最终故障样本：初始无响应探测 205.73 ms、位置变更时卡死 219.16 ms、预览状态变更时卡死 425.19 ms，均正确返回失败。另连续执行 200 次正常跨线程恢复，未出现假成功或坐标漂移。

系统已排队的异步操作不能撤回，目标恢复响应后仍可能完成该请求；超时不报告成功、不更新保存记录，也不无限重试。参考 [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)、[ShowWindowAsync](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync)、[WINDOWPLACEMENT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-windowplacement)。

WPF 夹具先完成加载，并在调度线程上连续观测 3 次稳定原生边界后发布 HWND，防止启动过程冒充稳态操作；该门槛本身没有消除 80 ms 超时问题，随后用诊断与重复运行证实并修复响应等待过短。这些更改未调整产品的几何或 UI。
